# Test Generators

Generate test cases for each of the 10 categories (7 standard + 3 infrastructure). Each category has specific rules for what to test and how to structure the tests.

## General Rules

1. **File naming:** `test_{category}.{ext}` where `{ext}` matches the project's test file extension:
   - Python: `.py`
   - TypeScript: `.test.ts`
   - JavaScript: `.test.js`
   - Go: `_test.go`
   - Java: `Test.java`

2. **File location:** In the service's `test_dir` from the project profile.

3. **Append, never overwrite:** If the file already exists, read it first and add new test functions at the bottom. Never remove or modify existing test functions.

4. **Match project patterns:** Read the service's existing test files (conftest.py, fixtures, helpers) to understand:
   - Import patterns
   - Fixture patterns
   - Assertion style
   - Test client setup
   - Mock patterns

5. **Docstrings:** Each generated test function gets a one-line docstring: `"""Generated by vibe-rescue: {what this tests}"""`

6. **Naming convention:** `test_{category}_{what}_{scenario}`
   - Example: `test_api_contracts_create_user_missing_email`
   - Example: `test_message_contracts_order_event_old_payload`
   - Example: `test_db_integrity_user_table_new_column_exists`

## Category: test_api_contracts

**Trigger:** Files classified as `api_layer` changed.

**How to discover what to test:**

1. Read the changed API files to find endpoint definitions:
   - Python/FastAPI: `@router.get`, `@router.post`, `@app.route`
   - Python/Flask: `@app.route`, `@blueprint.route`
   - Python/Sanic: `@app.route`, `@bp.route`
   - Node/Express: `router.get`, `router.post`, `app.get`
   - Go/Gin: `r.GET`, `r.POST`, `group.GET`

2. For each endpoint, extract:
   - HTTP method and path
   - Request body schema (if POST/PUT/PATCH)
   - Query parameters
   - Path parameters
   - Required vs optional fields
   - Field validation rules (type, min/max, regex)
   - Response schema
   - Auth requirements

**Tests to generate:**

For each endpoint found:

| Test | What it checks |
|------|---------------|
| `test_api_contracts_{endpoint}_{method}_success` | Happy path with valid input returns expected status |
| `test_api_contracts_{endpoint}_missing_{required_field}` | Each required field omitted returns 400/422 |
| `test_api_contracts_{endpoint}_invalid_type_{field}` | Wrong type for typed fields returns 400/422 |
| `test_api_contracts_{endpoint}_empty_{required_field}` | Empty string/null for required fields returns 400/422 |
| `test_api_contracts_{endpoint}_boundary_{field}` | Max length, numeric limits, boundary values |
| `test_api_contracts_{endpoint}_response_schema` | Response body matches expected structure |
| `test_api_contracts_{endpoint}_unauthorized` | Request without auth token returns 401 (if auth detected) |

## Category: test_message_contracts

**Trigger:** Files classified as `message_broker_layer` changed.

**How to discover what to test:**

1. Read the changed consumer/producer files
2. Find topic/queue names referenced
3. Find the payload schema (serializer class, dict structure, Marshmallow/Pydantic schema)
4. Check git diff for payload structure changes
5. Cross-reference with downstream consumers using the communication graph

**Tests to generate:**

| Test | What it checks |
|------|---------------|
| `test_message_contracts_{topic}_valid_payload` | Consumer processes a valid payload without errors |
| `test_message_contracts_{topic}_old_payload_compat` | Consumer handles the OLD payload structure (pre-change) without crashing. Construct the old payload from git history: `git show HEAD~1:{file}` |
| `test_message_contracts_{topic}_missing_optional_fields` | Consumer handles payload with optional fields omitted |
| `test_message_contracts_{topic}_missing_required_field` | Consumer rejects or dead-letters payload missing required fields |
| `test_message_contracts_{topic}_malformed_json` | Consumer doesn't crash on unparseable message |
| `test_message_contracts_{topic}_serialization_roundtrip` | Produce → serialize → deserialize → consume preserves all data |
| `test_message_contracts_{topic}_routing` | Message published to the correct topic name |
| `test_message_contracts_{topic}_dlq_routing` | Failed messages route to the correct dead-letter topic |

**Old payload construction:** To test backward compatibility, get the previous version of the payload:
```bash
git show HEAD~1:{path_to_schema_or_consumer_file}
```
Extract the old field structure and create a test payload matching it.

## Category: test_db_integrity

**Trigger:** Files classified as `data_layer` changed.

**How to discover what to test:**

1. Read the changed model/migration files
2. Find new/modified columns, tables, relationships
3. Scan ALL source files in the service for references to changed column names:
   ```bash
   grep -rn "{column_name}" {service_path}/ --include="*.py" --include="*.ts" --include="*.go" --include="*.java" | grep -v tests | grep -v __pycache__
   ```

**Tests to generate:**

| Test | What it checks |
|------|---------------|
| `test_db_integrity_{table}_{column}_exists` | Column exists in the ORM model |
| `test_db_integrity_{table}_{column}_nullable` | Column nullable setting matches migration |
| `test_db_integrity_{table}_{column}_default` | Column has expected default value |
| `test_db_integrity_{table}_{column}_all_code_paths` | Every file referencing the old column name has been updated. List all files found by grep. |
| `test_db_integrity_{table}_fk_{target}` | Foreign key references valid target table |
| `test_db_integrity_{table}_migration_reversible` | Migration can apply and rollback cleanly |

## Category: test_feature_flows

**Trigger:** Files classified as `business_logic` changed.

**How to discover what to test:**

1. Read the changed business logic files
2. Identify public functions and their signatures
3. Trace the data flow: input → processing → output
4. Identify error conditions and edge cases

**Tests to generate:**

| Test | What it checks |
|------|---------------|
| `test_feature_flows_{function}_happy_path` | Valid input produces expected output |
| `test_feature_flows_{function}_error_{condition}` | Each error path returns the correct error |
| `test_feature_flows_{function}_idempotent` | Same input twice produces same result (critical for consumers) |
| `test_feature_flows_{function}_state_transition` | State changes from initial → intermediate → final correctly |
| `test_feature_flows_{function}_empty_input` | Handles empty/null input gracefully |

## Category: test_feature_flags

**Trigger:** Files classified as `config_layer` changed, OR new env var references detected in diff.

**How to discover what to test:**

1. Find all env var / feature flag references in the changed files
2. Cross-reference: is each flag actually used in business logic?
   ```bash
   grep -rn "{FLAG_NAME}" {service_path}/ --include="*.py" --include="*.ts" --include="*.go" | grep -v config | grep -v tests
   ```

**Tests to generate:**

| Test | What it checks |
|------|---------------|
| `test_feature_flags_{flag}_used_in_code` | Flag is referenced in at least one business logic file (not just defined in config) |
| `test_feature_flags_{flag}_default_behavior` | Service behavior when flag is at its default value |
| `test_feature_flags_{flag}_enabled_behavior` | Service behavior when flag is non-default |
| `test_feature_flags_{flag}_unset_behavior` | Service doesn't crash when the flag env var is completely unset |

## Category: test_cross_service

**Trigger:** Message topic changes, shared model changes, or API contract changes detected. Only generated when `communication_graph` has edges for the affected service.

**How to discover what to test:**

1. From the communication graph, find all edges involving the affected service
2. For message broker edges: verify producer payload matches consumer expectation
3. For HTTP edges: verify client calls match server endpoint contract
4. For shared DB edges: verify both services handle the schema consistently

**Tests to generate:**

| Test | What it checks |
|------|---------------|
| `test_cross_service_{from}_{to}_contract_match` | Producer's output schema matches consumer's expected input schema |
| `test_cross_service_{topic}_routing_active` | Messages produced to the topic are actually consumed (topic name matches consumer subscription) |
| `test_cross_service_{from}_{to}_e2e_data_flow` | Data enters service A, exits correctly to service B |
| `test_cross_service_{topic}_dlq_routing` | Failed processing routes to the correct DLQ topic |

## Category: test_config_consistency

**Trigger:** Config files changed (config_parser, docker_config, env files, settings).

**How to discover what to test:**

1. Find all env vars referenced in code:
   ```bash
   grep -rnoP "os\.getenv\(['\"](\w+)['\"]\)" {service_path}/ --include="*.py" | grep -oP "'\K\w+(?=')"
   ```
2. Find all env vars defined in config files and docker-compose
3. Compare the two lists

**Tests to generate:**

| Test | What it checks |
|------|---------------|
| `test_config_consistency_env_var_{var}_defined` | Env var referenced in code exists in config/docker-compose |
| `test_config_consistency_config_parser_alignment` | Config parser args match runtime config class attributes |
| `test_config_consistency_runtime_modes` | Each MODE value (server/consumer/cron) has a valid handler |
| `test_config_consistency_consumer_types` | Each CONSUMER_TYPE value has a registered handler |

## Auto-Detected Additional Tests

If the project profile reveals these patterns, generate additional tests in the appropriate category file:

| Detected Pattern | File | Test |
|---|---|---|
| Encrypted fields (grep for `EncryptedField`, `encrypt`, `KMS`) | `test_db_integrity` | `test_db_integrity_encrypted_field_{name}_roundtrip` |
| Health endpoints (grep for `healthz`, `readyz`, `health`) | `test_api_contracts` | `test_api_contracts_health_endpoint_responds` |
| Caching (grep for `redis`, `cache`, `memcached`) | `test_feature_flows` | `test_feature_flows_{function}_cache_miss_fallback` |
| Pagination (grep for `limit`, `offset`, `page`, `per_page`) | `test_api_contracts` | `test_api_contracts_{endpoint}_pagination_params` |
| Auth middleware (grep for `auth`, `jwt`, `bearer`, `middleware`) | `test_api_contracts` | `test_api_contracts_{endpoint}_auth_required` |

Only generate these when the grep finds actual matches in the service's codebase.

## Multi-Service Parallelization

When the change manifest lists multiple `affected_services`:

1. Check if `dispatching-parallel-agents` skill is available (superpowers installed)
2. If YES: spawn one agent per service, each receiving only their portion of the change manifest
3. If NO: process services sequentially in the order they appear in the manifest
4. Cross-service tests run AFTER all per-service generation is complete

## Infrastructure Test Categories (--pro-mode)

Before generating infra tests, read `.vibe-rescue/memory.yaml` if it exists. Use values from `infrastructure` and `patterns` sections to populate template `# ADAPT:` markers automatically:
- `memory.infrastructure.postgres[].database` -> PostgreSQL database name
- `memory.infrastructure.clickhouse[].database` -> ClickHouse database name  
- `memory.infrastructure.kafka[].env_var` -> Kafka broker env var
- `memory.patterns.topic_naming_regex` -> topic naming pattern
- `memory.patterns.topic_prefix` -> topic prefix for grep patterns
- `memory.patterns.consumer_config_path` -> path to consumer config file

If memory has no value for a marker, leave the `# ADAPT:` comment as a manual fallback.

The following 3 categories are only generated when `--pro-mode` is passed. They require real Docker containers running and connect to actual databases/brokers.

All infrastructure tests use two-level markers: `@pytest.mark.infra` (general gate) plus a specific marker (`@pytest.mark.infra_postgres`, etc.). Without `--pro-mode`, all infra tests auto-skip via `pytest_collection_modifyitems`.

### Category: test_infra_postgres

**Trigger:** `--pro-mode` + service has SQLAlchemy models (files importing `DeclarativeBase`, `declarative_base`, or `Column` from sqlalchemy).

**How to discover what to test:**

1. Find all model classes:
   ```bash
   grep -rn "class.*Base.*:" {service_path}/db/models.py {service_path}/models/ --include="*.py" 2>/dev/null
   ```
2. For each model class, extract: `__tablename__`, column definitions, primary keys, foreign keys, nullable constraints
3. Group models by database using connection string env vars or `__bind_key__`
4. Use the `templates/test_infra_postgres.py` template as the base

**Tests to generate:**

| Test | What it checks |
|------|---------------|
| `test_infra_postgres_table_exists[{Model}]` | Table from `__tablename__` exists in real DB (parametrized per model) |
| `test_infra_postgres_columns_match_model[{Model}]` | Every column in the SQLAlchemy model exists in the real table |
| `test_infra_postgres_nullable_constraints_match[{Model}]` | Model nullable settings match DB nullable constraints |
| `test_infra_postgres_primary_keys_match[{Model}]` | Model PKs match DB PKs |
| `test_infra_postgres_foreign_keys_exist[{Model}]` | FK constraints in model exist in DB |
| `test_infra_postgres_no_orphaned_columns[{Model}]` | DB columns not in model are flagged (warn only, not fail) |
| `test_infra_postgres_seed_data_{table}` | Essential seed data tables are non-empty (init scripts ran) |

**Validation pattern:** Use `sqlalchemy.inspect(engine)` for DB introspection, `sqlalchemy.inspect(ModelClass)` for model introspection. Compare column-by-column.

**Fixture requirements:**
- Session-scoped engine fixture per database with `pytest.skip()` on connection failure
- `pool_pre_ping=True` for connection resilience
- Sync driver (`psycopg2`) for schema introspection even if the service uses async

**Template:** `templates/test_infra_postgres.py`

### Category: test_infra_clickhouse

**Trigger:** `--pro-mode` + service imports `clickhouse_driver`, `asynch`, or references ClickHouse env vars (`CLICKHOUSE_*_HOST`).

**How to discover what to test:**

1. Find ClickHouse table references:
   ```bash
   grep -rn "FROM\|INSERT INTO" {service_path}/ --include="*.py" --include="*.sql" | grep -vi "test\|__pycache__" | grep -oP "FROM\s+\K\w+\.\w+" | sort -u
   ```
2. Classify tables as: base (must exist), distributed (warn if missing in single-node), materialized views (warn if missing)
3. Extract expected columns from migration DDL or query patterns
4. Use the `templates/test_infra_clickhouse.py` template as the base

**Tests to generate:**

| Test | What it checks |
|------|---------------|
| `test_infra_clickhouse_base_table_exists[{table}]` | Base table exists in database (FAIL if missing) |
| `test_infra_clickhouse_distributed_table_exists[{table}]` | Distributed table exists (WARN + skip if missing in single-node) |
| `test_infra_clickhouse_materialized_view_exists[{view}]` | Materialized view exists (WARN + skip if missing) |
| `test_infra_clickhouse_{table}_has_all_columns` | Expected columns from migration DDL exist in the real table |
| `test_infra_clickhouse_{table}_column_types` | Column types match expected types (UInt16, String, etc.) |
| `test_infra_clickhouse_query_table_exists[{table}]` | Tables referenced in query constants exist |

**Validation pattern:** Query `system.tables` and `system.columns` with `database = '{db_name}'` filter. Use `clickhouse_driver.Client` (sync) for simplicity.

**Mixed fail/warn strategy:** Base tables FAIL if missing. Distributed tables and materialized views WARN + skip (single-node Docker won't have them).

**Template:** `templates/test_infra_clickhouse.py`

### Category: test_infra_kafka

**Trigger:** `--pro-mode` + service has Kafka consumer/producer config (imports `confluent_kafka`, `aiokafka`, `kafka`, or `eventbridge`).

**How to discover what to test:**

1. Find consumed topic names:
   ```bash
   grep -rn '"topic"\|"subscribe"\|"consume"' {service_path}/ --include="*.py" --include="*.ts" --include="*.go" --include="*.java" | grep -oP '"([a-z][-a-z0-9_.]+)"' | sort -u
   ```
2. Find produced topic base constants in `common/constants.py` or equivalent
3. Parse `consumer_config.py` to count active (non-commented) topic entries
4. Use the `templates/test_infra_kafka.py` template as the base

**Tests to generate:**

| Test | What it checks |
|------|---------------|
| `test_infra_kafka_broker_is_reachable` | Broker responds to list_topics() |
| `test_infra_kafka_broker_cluster_info` | Cluster metadata is retrievable |
| `test_infra_kafka_{group}_topic_exists[{topic}]` | Each consumed topic exists in broker (parametrized) |
| `test_infra_kafka_produced_topic_base_can_create[{base}]` | Produced topic base creates valid topics |
| `test_infra_kafka_topic_name_follows_convention[{topic}]` | Topic names match naming regex pattern |
| `test_infra_kafka_all_config_topics_exist_in_broker` | consumer_config.py topics exist in broker |
| `test_infra_kafka_consumed_topic_count_matches` | Expected topic count matches config file |

**Topic pre-creation:** In local Docker where `auto.create.topics.enable=true`, topics may not pre-exist. Use `_ensure_topics_exist()` helper to create missing topics before validation. This tests the naming contract, not just existence.

**Fixture requirements:** Session-scoped `kafka_admin` via `KafkaAdminClient` with `request_timeout_ms=10000`. Skip gracefully if broker unreachable.

**Template:** `templates/test_infra_kafka.py`
