# Fix Loop

Evaluate test failures, classify their root cause, propose or apply fixes, and loop until stable.

## Failure Classification

For each failing test, determine the root cause category:

### Step 1: Read the Test and Its Output

```bash
# Run the single failing test with verbose output
{test_command} {test_file}::{test_function} -v --tb=long 2>&1
```

Capture:
- The assertion that failed
- The expected value
- The actual value
- The traceback

### Step 2: Classify the Failure

Walk this decision tree in order:

```
1. Is this a HAND-WRITTEN test (not in a test_{category} file)?
   YES -> Category: HAND_WRITTEN
   NO  -> continue

2. Is the failing test asserting behavior that the design spec says SHOULD have changed?
   (Check: does the spec describe new behavior that contradicts the test's assertion?)
   YES -> Category: STALE_TEST (test needs updating, not the code)
   NO  -> continue

3. Is the test asserting behavior that matches the spec, but the code produces wrong output?
   YES -> Category: CODE_BUG (real bug in the code)
   NO  -> continue

4. Is the test itself broken (import error, fixture missing, wrong setup)?
   YES -> Category: TEST_INFRASTRUCTURE (test needs fixing)
   NO  -> continue

5. Is the failure in a `test_infra_*` file (infrastructure validation test)?
   YES -> Category: INFRA_DRIFT
   NO  -> continue

6. Is this a backward compatibility violation?
   (Check: does an OLD test fail because new code changed behavior the spec says must be preserved?)
   YES -> Category: BACKWARD_COMPAT_VIOLATION
   NO  -> Category: CODE_BUG (default)
```

## Action Per Category

### HAND_WRITTEN

**Both modes:** ALWAYS ask user before modifying. Show the failure, the proposed fix, and ask:

"Hand-written test `{test_name}` is failing. This test was not auto-generated by vibe-rescue. Proposed fix: {diff}. Apply this change? (yes/no)"

Never auto-modify hand-written tests, even in `--auto-run` mode.

### STALE_TEST

The test's assertion is outdated -- the code intentionally changed this behavior.

**Default mode:**
1. Show the diff between old and new expected values
2. Explain: "This test expected `{old_value}` but the spec says the new behavior is `{new_value}`"
3. Show the proposed test fix
4. Wait for user approval

**Auto-run mode:**
1. Auto-fix the test assertion to match the new expected behavior
2. Re-run ALL tests to verify the fix doesn't break anything else
3. Log the fix in the report

### CODE_BUG

The test is correct but the code has a bug.

**Default mode:**
1. Analyze the failing code path
2. Show proposed code fix as a diff preview -- DO NOT APPLY
3. Display: "Tip: Run with --auto-run to automatically fix and re-run until stable"
4. Wait for user approval
5. If approved: apply fix, re-run ALL tests

**Auto-run mode:**
1. Analyze the failing code path
2. Apply the code fix
3. Re-run ALL tests (not just the fixed one)
4. Track fix attempts per issue:
   - If this is attempt 1-3: continue
   - If this is attempt 4+: STOP, escalate to user:
     "Failed to fix `{test_name}` after 3 attempts. Last error: {error}. Please investigate manually."
5. After each fix, check if any PREVIOUSLY PASSING tests now fail:
   - If YES: REVERT the fix immediately (`git checkout -- {file}`), escalate to user:
     "Fix for `{test_name}` caused regression in `{other_test}`. Reverted. Please investigate."
   - If NO: continue

### TEST_INFRASTRUCTURE

Test setup is broken (missing import, fixture, conftest issue).

**Both modes:** Fix the test infrastructure (add missing import, fix fixture). These are always safe to auto-fix since they don't change behavior.

### BACKWARD_COMPAT_VIOLATION

Old behavior changed when the spec says it must be preserved.

**Both modes:** ALWAYS STOP. This is a real bug -- the code broke backward compatibility.

Display:
```
BACKWARD COMPATIBILITY VIOLATION

Spec: {spec_ref}
Required: backward compatible
Failing test: {test_name}
Expected: {old_behavior}
Actual: {new_behavior}

The code changed behavior that the spec says must remain compatible.
This must be fixed in the code, not in the tests.
```

If `backward_compatibility.required` is `unknown` (no spec found):
- Ask the user: "Is backward compatibility required for this change? (yes/no)"
- If yes: treat as BACKWARD_COMPAT_VIOLATION
- If no: treat as STALE_TEST

### INFRA_DRIFT

The test detected a mismatch between code models and real infrastructure (missing table, missing column, missing topic, type mismatch).

**Both modes (default AND auto-run):** NEVER auto-fix infrastructure drift. Infrastructure changes (migrations, topic creation, schema changes) have wide blast radius and are out of scope for the test fix loop.

Display:
```
INFRASTRUCTURE DRIFT DETECTED

Test: {test_name}
System: {PostgreSQL | ClickHouse | Kafka}
Expected: {what the model/code expects}
Actual: {what the real infrastructure has}

This requires a migration or manual fix, not a code change.
Suggested remediation:
  - {specific action: "Run migration X", "Create topic Y", "ALTER TABLE ADD COLUMN Z"}
```

In `--auto-run` mode: skip this failure, continue with remaining tests, and include all infra drift issues in the final report summary.

## The Fix Loop

### Default Mode

```
start:
  run ALL tests
  if all pass -> go to report
  for each failure:
    classify (see decision tree above)
    show proposed fix
    wait for user approval
    if approved: apply fix
  re-run ALL tests
  if all pass -> go to report
  if same tests still fail -> show updated context, propose different fix
  goto start
```

### Auto-Run Mode

```
start:
  attempt_count = {}  # track attempts per test
  run ALL tests
  if all pass -> go to report
  for each failure:
    classify (see decision tree above)
    if HAND_WRITTEN or BACKWARD_COMPAT_VIOLATION -> STOP, escalate
    attempt_count[test_name] += 1
    if attempt_count[test_name] > 3 -> STOP, escalate
    apply fix
    run ALL tests
    if new failures introduced -> REVERT, STOP, escalate
    if all pass -> go to report
    goto start
```

## Fix Strategy Resolution

The fix strategy depends on available plugins:

| Plugin Available | Fix Strategy |
|---|---|
| superpowers (systematic-debugging) | Invoke systematic-debugging skill for root cause analysis before proposing fix |
| standalone | Analyze the code path directly: read the failing function, trace inputs/outputs, propose minimal fix |

## Safety Invariants

These rules CANNOT be overridden, even by `--auto-run`:

1. **Never auto-modify hand-written tests** -- always ask user
2. **Never ignore backward compatibility violations** -- always stop and report
3. **Max 3 attempts per issue** -- then escalate
4. **Revert on regression** -- if a fix breaks other tests, undo it immediately
5. **Re-run ALL tests after every fix** -- never assume only the fixed test matters
6. **Never delete test functions** -- only modify assertions or add new tests
7. **Never auto-fix infrastructure drift** -- always escalate with diagnostic context and suggested remediation
